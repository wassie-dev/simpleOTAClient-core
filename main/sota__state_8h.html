Detailed Description

Everything a client persists, and the order it is written.

These keys are a contract with every release in the field: docs/NVS_CONTRACT.md has the rules for changing them.

Keys in the store (sota_kv.h). A key keeps its name and meaning in every release; docs/NVS_CONTRACT.md has the release that first wrote each one:

sota_build u32 build number of the live (reported) image sota_hash str sha256 hex of the live image sota_ver str version label of the live image sota_image str fingerprint of the image the live identity was last seen running on (sota_boot_info_t.image_id) sota_trial u8 0 steady, 1 trial, 3 trial that has booted, 2 rolled back with a report pending sota_staged u8 present while the trial record is written but the boot slot has not switched yet (sota_trial.h) sota_new_part u32 flash address the update went to sota_prev_part u32 flash address the update replaced sota_prev_build u32 \ sota_prev_hash str > identity before the update, for a rollback sota_prev_ver str / sota_fail_dep str deployment the confirmed / rolled_back report names sota_fail_build u32 build that report names sota_conf_pend u8 1 until the record's confirmed report is queued sota_rb_reason str why sota_trial is 2; missing means confirm_timeout sota_outbox blob sota_outbox_t: reports waiting to be sent

The functions return false when a write did not reach storage. None of them logs: what to do about a failure is the caller's call.

◆ sota_state_stage_trial()

bool sota_state_stage_trial ( const sota_identity_t *  prev,
const sota_identity_t *  next,
uint32_t  new_part,
uint32_t  prev_part,
const char *  deployment 
)

Write the trial record before the boot slot switches, so a bootable new image always has one: sota_staged first, then both partitions and the previous identity, then the new identity and report context, and sota_trial last.

On a failure the record is dropped again, and the previous identity put back once it had been saved in full.

prev is the identity being replaced; next the update's. Returns false when the record could not be written; the slot must not switch then.

◆ sota_state_mark_rolled_back()

bool sota_state_mark_rolled_back ( const sota_state_t *  st,
const char *  reason

The trial is being rolled back: the previous identity goes live, and sota_trial becomes 2 with the reason, for the next boot to report.

Restores unconditionally: zero and empty are valid fresh-device values, and skipping them would leave a rolled-back device reporting the new build, which the server would then never offer again.
